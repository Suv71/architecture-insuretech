### Сервис osago-aggregator

### Требуется ли ему своё хранилище данных?

Так как был выбран синхронно-асинхронный способ взаимодействия с **osago-aggregator**, то БД понадобится для сохранения запросов на расчет по конкретным заявкам и отправку результата через Transactional Outbox. 

### Какой API он предоставляет core-app?

Он предоставляет Rest API для создания запроса на расчет ОСАГО с конкретными параметрами, который передает клиент. В ответ он получается id запроса, по которому он будет ожидать результаты по каждой компании.

### Определите средство интеграции между сервисами core-app и osago-aggregator.

Приложение **core-app** делает синхронный запрос на создание расчетов по конкретной заявке и в ответ получает id запроса.

Сервис **osago-aggregator** после получения запроса начинает опрашивать страховые и при получении ответа или не получении в течении 60 секунд отправляет событие с результатом расчета, которое
получит **core-app**. Получается на один расчет будет количество сообщений равное количеству страховых.

### Подумайте над API для веб-приложения в core-app.

Взаимодействие с веб-приложения с **core-app**, то, что касается получения списка страховых компаний перед отправкой
заявки, будет по REST. Но, после нажатия кнопки "Получить предложения", будет устанавливаться WebSocket с получением
ответов от каждой страховой по мере готовности предложений от каждой компании. На расчет должно уйти около 60 секунд.

### Определите средство интеграции между веб-приложением и core-app.

Предлагаю сделать Client pull с использованием REST для всего веб-приложения и Server push по WebSocket для получения
предложений после отправки заявки.

### Применение паттернов отказоустойчивости.

- Rate Limiting для ограничения запросов на создание заявок по расчету ОСАГО, сейчас у нас максимум 2500 одновременных клиентов
- Retry на случай разрыва WebSocket или ошибки от какой-то страховой компании
- Timeout для ограничения длительности запросов в сервисы внешних компаний и в **core-app** при расчете

### Примите во внимание, что сервисы задеплоены в нескольких экземплярах.

Текущая схема взаимодействия поддерживает работу в нескольких экземплярах за счет наличия реплицированной БД у **osago-aggregator**, работе с брокером сообщений, а также механизмом Service Mesh, который позволяет направлять трафик в разные экземпляры приложений.
